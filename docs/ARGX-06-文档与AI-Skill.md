### 3.3 专业化标准（照着 `nonebot.dev/docs/` 的方法，别照抄它的排版）

打开它看一遍，你要学的是**这六条**：

1. **标题即索引**：小节标题是名词短语，能直接当目录用。**不用**「三步让它动起来」
   「不对的时候先看这里」这类悬念式标题。
2. **术语优先，比喻退场**：能用术语说清的就用术语。比喻只保留在首页产品文案里。
3. **示例先于解释**：每个能力先给可复制的代码，再讲参数。
4. **能表格化的就表格化**：参数、命令、错误码、常量一律用表，不用散段落。
5. **第二人称统一用「你」**，但**不出现语气词**：删掉「其实」「说白了」「压根」
   「别忘」「对了」「顺便说」。
6. **不出现反问与感叹**：把「你确定是这三个数字吗？」这类交互文案（那是 demo 剧本里的，
   不属本文档）与「灯一直在闪等于没闪」这类修辞，改成陈述句。

**标题改法对照（这 10 页 + 分组名都要过一遍）**：

| 现在 | 改成 |
|---|---|
| 快速开始 / 「三步让它动起来」 | 快速开始 / 「安装与首次点亮」 |
| 连接方法 / 「电脑侧怎么连上装置」 | 连接方法 / 「电脑侧连接装置」 |
| 接入 SDK / 「把 ARGX 接进你的作品」 | 接入 SDK / 「在作品中接入 SDK」 |
| 指令与参数 / 「一条 cue 能带什么」 | 指令与参数 / 「cue 帧与参数」 |
| 回执与去重 / 「装置回了什么」 | 回执与去重 / 「回执、幂等与重传」 |
| 指令表 / 「全部命令」 | 指令表 / 「命令参考」 |
| 错误码 / 「err 帧的五个码」 | 错误码 / 「错误码参考」 |
| 故障排查 / 「不对的时候先看这里」 | 故障排查 / 「故障排查」 |
| 常量总表 / 「一页记住所有数字」 | 常量总表 / 「常量参考」 |

> 上面是**方向**，不是最终定稿。你在改写时如果发现有更准确的术语，以你判断为准；
> 但**口语化标题一律要换掉**。

### 3.4 控制台文本去 AI 味（**定点修改，不许整篇重写**）

用户反馈：「**我选中的这种内容太 ai 了**」。同时明确：**「大部分已经写的不错了只需要小改。」**

这一条是**独立的一件**，不要和 3.3 的标题专业化混在一起做——
标题问题是「结构不专业」，AI 味是「句子的生成痕迹」，两类问题两种改法。

#### 3.4.1 目标与边界

**目标只有两个词：清晰、正式。**

- **清晰**：一句话一个意思；术语准确；条件与边界写全（「当前固件」「缺省值」「上限」）；
  读者看完能直接照着做、或照着判断。
- **正式**：陈述句为主；无语气词、无口语提示词、无修辞、无情绪。

> ⚠️ **通用「去 AI 味」教程里有大量建议，本项目明确不采纳。**
>
> 那些教程的目标是「读起来像真人在聊天」，常见建议是「口语化」「加个人轶事」
> 「允许反问」「表达立场与情绪」「长短句随意交错」。**这套东西会把技术文档拉成博客**，
> 与本阶段「专业化」的目标正好相反。
>
> 判断标准一句话：**不要像「人写的」，要像「一个人写的正式技术文档」。**

参考来源（挑条目用，**照抄前先按上面的判断标准过滤**）：
Wikipedia《Signs of AI writing》——最全的清单，分语气 / 结构 / 格式 / 引用四类；
Dragonfly Editorial《AI Tells, and How to Fix Them》——句子级的例子最多。

#### 3.4.2 病征清单（四类，逐类扫）

**A. 句子级**（最常见，优先扫这一类）

| 病征 | 真实例子 / 形态 | 改法 |
|---|---|---|
| **自证与辩护** | 「这是固件实现到什么程度的问题，**不是协议设计的问题**」 | 替读者先辩解一遍是多余的。删，只留事实 |
| **否定式抬高**（"It's not just X — it's Y"） | 「这**不只是**一盏灯，**而是**房间的情绪」 | 删掉前半句的比较，直接说后半句 |
| **括号 / 破折号堆叠** | 「协议支持连续强度（i 是 0~1 的小数，虚拟装置会按它做渐变），但当前固件是二值的——i > 0.02 就……」 | 一句里 ≥2 处插入语就拆成独立句 |
| **空泛承诺** | 「**将来**固件换成带 DAC 的驱动，这一路的强度就**自然生效了**」 | 删未来时。除非有明确条件，否则不写 |
| **具体句末挂泛化目的** | 「……**以帮助**你的组织保持敏捷」这类尾巴 | 砍掉尾巴，让细节自己说话 |
| **元评论 / 路标语** | 「需要注意的是」「值得一提的是」「换句话说」「这点很重要」 | 直接进入正题 |
| **口语提示词** | 「声音这一路**要特别说一句**」；同类的「顺便说」「说白了」「其实」 | 直接进入正题 |
| **对仗凑节奏** | 「真机上声音只有"响/不响"」 | 平实说：「真机上只有有声与静音两种状态」 |
| **防御性后缀** | 「这个区别贯穿整个系统，**不是界面上的装饰**」 | 删掉后半句 |
| **情绪化收尾** | 「这才是……的关键」「真正重要的是……」 | 删 |
| **「无论你是 A 还是 B」式开头** | 「无论你是新手还是老手，都能……」 | 删掉从句，直接说主体 |

**B. 段落级**

| 病征 | 形态 | 改法 |
|---|---|---|
| **一段讲三件事** | 同一段混了「协议怎么定义 / 固件怎么实现 / 模拟器与真机差异 / 未来怎么办」 | 拆成「一句结论 + 一张表」 |
| **段末用破折号收尾** | 「……——通过协作与调整，一切都会好起来」 | 删掉收尾那半句，让信息自己站住 |
| **重复已知信息** | 表格里已写过的数字，段子里再说一遍 | 删段子里的重复 |
| **三段式排比** | 「不仅……更是……」「一方面……另一方面……」；堆三项凑节奏 | 拆掉排比；并列超过三项就改成表格 |
| **泛化开头** | 第一句是不说也知道的常识 | 删，从第二句起 |
| **段落结构全都一样** | 每段都是「泛化句 → 三项列表 → 破折号收尾」 | 打散；同一形态连续出现两次就换写法 |

**C. 词表级（中文高频套话，见一个删一个）**

```
综上所述  值得注意的是  值得一提  不难发现  众所周知  总而言之
除此之外  换句话说  这意味着  更重要的是  需要注意的是
随着……的发展  在……的背景下  在当今时代
赋能  抓手  闭环  颗粒度  底层逻辑  落地  堪称  无疑  至关重要  旨在
```

**D. 标点级**

- **破折号「——」是头号标记。** 单页超过 3 处就逐处查，多数情况下可改成句号或逗号。
- **项目符号不要滥用**：不是列表形状的内容写成段落。连续三项都是完整句子的列表，
  其实就是一个段落，别加符号。

**上面那个病例子就是用户截图里选中的那段。** 一段话里同时犯了前三条，
这正是要修的典型。改后参照：

```
当前固件的强度是二值的：i > 0.02 输出 2.7kHz 方波，否则静音。
虚拟装置按 i 做渐变，所以模拟器里能看到强度差异，真机上只有有声与静音两种状态。
协议侧 i 仍是 0~1 的连续值，换成带 DAC 的驱动即可生效，协议不需要改。
```

三句话，事实一条不少，自证与承诺全部去掉。

#### 3.4.3 硬约束

1. **禁止整篇重写。** 用户明确说「大部分已经写的不错了只需要小改」。
   整篇重写会连带毁掉写得好的部分，而且重写出来的文本很可能带**新的** AI 味。
   只动有病征的句子。
2. **不许因为去 AI 味而丢技术信息。** 数字、参数名、条件、限定词
   （「当前」「缺省」「上限」「真机上」）一个都不能少。
   **宁可留着不优雅，不许留着不准。**
3. **一处改动要能指出删了什么病征。** 收尾时给「改动前后对照表」，
   逐处写：位置 / 原文 / 改后 / 删掉的病征（对上 3.4.1 的表）。
4. **一条改动只解决一类问题。** 标题归 3.3，AI 味归本节，技术内容归 3.5 的搬运。
   混在一起写，对照表就说不清。

**③ 一句话数一遍插入语**

```bash
grep -rn "（[^）]*）" guide/ | awk -F'（' 'NF>2'   # 一行两处以上括号
```

**三条判定规则**（简单可执行）：

1. **一段超过 3 句就考虑拆。**
2. **一句里有 ≥2 个括号或破折号就重写那一句。**
3. **「不是……而是……」如果只是修辞、不是技术对比，删掉后半句。**

**三个「读一遍」测试**（前两条来自那两份参考清单，很有效）：

1. **删除测试**：把这一句整个删掉，段落是否丢失了实际信息？**不丢就删。**
2. **首末句测试**：只读每段的第一句与最后一句。若同义，删掉其中一句。
3. **念出来测试**：读出声。耳朵能立刻抓到「这句太长」和「这里转折很硬」——
   眼睛会滑过去。

#### 3.5.3 生成器 `tools/build-guide.mjs`

- **零依赖**，纯 Node。**禁止**引入 `marked` / `remark` / `markdown-it` 等任何 md 解析库——

- 与 `tools/site.mjs` 同风格：中文注释、断言失败直接 `process.exit(1)`。
- 两种模式：
  - `node tools/build-guide.mjs` —— 生成 `console/src/data/docs.generated.ts`
  - `node tools/build-guide.mjs --check` —— **不写文件**，比对「md 生成的期望内容」与
    「磁盘上的生成物」，不一致就打印差在哪一页并非零退出
- 生成物头部必须写死一段注释：

  ```

  //    改文档请改 guide/ 下的 md，然后跑 node tools/build-guide.mjs

- 生成物形状**与现在的 `docs.ts` 完全一致**：导出 `DOC_GROUPS`、`DOC_PAGES`。
  `DocPage` / `DocBlock` 类型与 `docBySlug()` **搬到 `console/src/data/docs.types.ts`**
  （手写文件，生成物 `import type` 它），这样类型定义不会被生成器覆盖。
- `Docs.tsx` 的改动应该极小：把 `from '../data/docs'` 改成从 `docs.generated` 取数据、
  从 `docs.types` 取类型。**组件逻辑一行都不用改。**

#### 3.5.4 接线

- `console/package.json` 加两个脚本，保证 dev 与 build 前一定先重新生成：

  「clone 下来就能跑」，提交生成物让任何人 clone 后不跑任何脚本就能起 dev。

- **CI 加一条断言**：`.github/workflows/test.yml` 的 `console` job 里加

  注意路径；或直接写在根目录步骤里）。**不一致就红**，防止有人手改生成物或忘记重生成。

### 3.8 三档语域（**件一至件七全部受它约束，动笔前先读这一节**）

用户的要求原话：

> 「要是给玩家看的就把文字写得可爱一点（当然要适度，这样 AI 味淡）；
> 给创作者看的、开发者看的就参考 nonebot 文档那样写。
> 控制台里的文档用中文书写，只有仓库里的 README 写英语、中文两版。」

「去 AI 味」不是一种写法，**是先定语域再定写法**。同一个项目里有三种读者，
句子该长该短、该用什么词，都不一样。
**动笔前先答一句：这段话写给谁、他要拿它做什么。**

| 档 | 读者 | 他要做什么 | 语气 | 本项目里对应哪些文案 |
|---|---|---|---|---|
| **R1 玩家向** | 用产品的人 | 照做、看懂正在发生什么 | 轻快、具体、**克制地可爱** | 首页产品文案（件六）、控制台里模拟器 / 设备 / ARG 库三页的界面文案 |
| **R2 创作者向** | 用 SDK 做网页的人（多半让 AI 代写代码） | 复制代码、查参数 | 正式技术文档，**中文** | `guide/` 全部 10 页、`sdk/README.md`、`sdk/AGENTS.md` |
| **R3 开发者向** | 读协议、改固件、看源码的人 | 判断实现、参与贡献 | 技术参考，**英文**（README 另配中文版） | 三个仓库的 `README.md`、`protocol/PROTOCOL.md`、`firmware/` 与 `device/` 的注释 |

> **通用底线（三档都适用）：清晰永远优先于风格。**
> 一句话让人看不懂，写得再可爱、再专业都是负分。

#### 3.8.1 R1 玩家向：可爱从哪来

**从具体、短句、画面感来，不从语气助词来。**

| 可爱来自 ✅ | 可爱不来自 ❌ |
|---|---|
| 具体动作：「把线插上，它会亮一下，表示它醒了」 | 语气词：「插上就好啦～」 |
| 短句 + 一个画面：「灯在等你」 | 撒娇后缀：「灯灯在等你哦」 |
| 给玩家留余地：「没插装置也能玩完，只是房间里安静了点」 | 夸张承诺：「超震撼的沉浸体验！！」 |
| 拟人但准确：「装置正在自检，大概 2 秒」 | 含糊拟人：「装置正在乖乖准备中…」 |

**红线（一出现，可爱就变廉价）**：

- **不用 emoji**——工具界面里的 emoji 会破坏图标体系与视觉一致性。
- **不用波浪号 `～`**、不用叠词卖萌（「亮亮」「慢慢来哦」）。
- **不用感叹号**，更不连用。要表达力量感就用短句。
- **不把语气词堆在句尾**（「呀 / 啦 / 哦 / 呢 / 嘛」）。
- **不叫用户「小可爱」「宝子」**，也不自称「小助手」。
- **操作步骤不许可爱化**。凡是让玩家照着做的（连接步骤、报错原因、参数含义），
  必须清楚到一眼看懂——**可爱只能加在状态描述与鼓励语上**。

**一条判定**：把这句话念给一个 12 岁的人听，他能立刻知道下一步做什么吗？
能，且不觉得被哄——合格。

```
❌ 装置正在乖乖等待连接哦～请把小可爱插上电脑吧！
✅ 装置还没有连上。把 USB 线插到电脑上，然后点「连接」。

❌ 太棒了！！灯已经成功亮起来啦～
✅ 灯亮了。现在可以翻到下一页。
```

第二条为什么合格：**「灯亮了」本身就是玩家最想看到的结果**，
它比任何形容词都更有情绪。可爱来自「说中了玩家此刻的感受」，不是来自语气。

#### 3.8.2 R2 创作者向：中文技术文档

**主体规则就是 3.3 那六条 + 3.4 那四类病征**，这里只补三条 3.3/3.4 没写的：

| # | 规则 | 反例 → 正例 |
|---|---|---|
| 1 | **不用「请」**，不用拉丁缩写（`i.e.` `e.g.` `etc.`） | 「请运行」→「运行」；「e.g.」→「例如」 |
| 2 | **不拟人化** | 「该功能让你能够控制灯光」→「使用该功能可以控制灯光」 |
| 3 | **条件在前，指令在后** | 「运行该命令，如果你已经装了 Node」→「装了 Node 之后，运行该命令」 |

**中文技术文档里三个高频病征**（3.4 已列，这里点名它们最常混进 `guide/`）：

- **口语残留**：「要特别说一句」「才算数」「就算过」「别忘」「顺便」——
  这些在聊天里是有效载荷，在参考文档里是噪音。**直接删，不替换。**
- **含糊限定**：「大概」「应该是」「差不多」→ 给具体条件或数字。
- **子虚乌有的承诺**：「将来会支持」→ 删。**没实现就不要写。**

**什么时候可以用一句比喻**：只有一处——这个概念第一次出现、且比喻能省掉一整段解释时。
用完立刻回到术语。参考文档里比喻是注释，不是文体。

#### 3.8.3 R3 开发者向：英文技术写作

沿用 R2 的全部规则，换成英文技术写作习惯：

- **第二人称 `you`**、主动语态、一般现在时。
- **标题用 sentence case**（`Get started`，不是 `Get Started`）。
- **不预宣告**：`Coming soon` / `In a future release` 一律不写。
- **不用 `please`**、不用感叹号。
- **不把产品当人**：不写 `ARGX lets you…`，写 `You can use ARGX to…`。
- **每个代码块必须真能跑**。跑不通的示例不要放。
- **不许 overclaim**：没验证过的事必须写没验证过（硬件仓那条尤其）。

**英文 AI 高频词黑名单**（在写英文 README 时逐词过一遍）：

```
delve  leverage  robust  seamless  unlock  empower  elevate  harness
tapestry  landscape(喻义)  navigate the complexities  cutting-edge
revolutionary  game-changing  at its core  in today's fast-paced world
it's worth noting  it's important to note  let's dive in
```

替换思路：**换成具体动词 + 具体对象**。
`leverage the SDK` → `use the SDK`；`seamless integration` → `one line of code`。

**双语版本不要逐句直译**（这条对件七最重要）：
中文版与英文版**内容等价、句子各写**。中文读者习惯的省略、顿号、「即」「需」「无需」
这类紧凑写法，直译成英文会变生硬；英文的长从句直译成中文也会变啰嗦。
**给两版各写一遍，保证事实（数字、参数名、命令、状态）一致即可。**

#### 3.8.4 自检：换档之后回头核一遍

1. **语域有没有串**：玩家向的文案里冒出「参数」「回执」「协议」，= 串档了。
2. **删掉形容词后句子还成立吗**：`超震撼的沉浸体验` → 删完什么也没剩下，= 空话。
3. **一句话里有几个插入语**：≥2 个就拆。
4. **把这段给读者，他能照做吗**：这是唯一真正的验收标准。

## 4. 第四件：新建 `argx-skill` 仓库

### 4.1 定位

**给「已经在写 ARG 解密网页的作者」的 AI 助手用的技能包。**

使用者不是硬件作者，也不是 ARGX 开发者，而是**一个手里有网页源码、想让房间里的灯跟着
剧情动的创作者**。他把这个 skill 交给自己的 AI 助手，AI 读完他的网页代码，
按规范把 ARGX 接入进去。

**硬要求：这个仓库必须自包含。** AI 读完它就应该能写出正确的接入代码，
**不需要跳到主仓去查协议**。所以协议、SDK API、事件词表、参数表、错误码、常量，
都要在仓库里能查到（见 4.3）。

### 4.2 仓库结构

建议结构（命名可以微调，但**每一条都要有**）：

```
argx-skill/
  SKILL.md                    入口：这是什么、五步流程、两种模式怎么选、什么时候读哪个文件
  references/
    protocol.md               协议参考（副本，见 4.8）
    sdk.md                    SDK API 全集（init/connect/fire/cue/batch/reset/state/on/hint…）
    event-vocabulary.md       六个事件词的语义、会动什么、优先级
    parameters.md             i / dur / ramp / pri / hold 五个参数
    errors.md                 五个错误码
    constants.md              心跳 3s、掉线 10s、看门狗 15s、TTL 上限 30s、batch 上限…
    placement.md              埋点规范：3–8 个、只在情绪转折点、不许发引脚电平
    hardware-limits.md        当前固件实现到什么程度（声音那路实际是二值、真机未验证）
  prompts/
    mode-a-discuss.md         模式一：与创作者讨论实现细节
    mode-b-autonomous.md      模式二：问清偏好后完全自主生成
    verify.md                 检验：核对生成结果是否符合 ARGX 规范
  assets/
    argx.js                   SDK 源码（副本，见 4.8）
    argx.d.ts                 类型声明（副本）
  LICENSE                     MIT
  README.md                   给「人」看的：怎么用、怎么交给自己的 AI
  tools/check-skill.mjs       自检脚本，见 4.10
  .github/workflows/ci.yml    跑 check-skill
```

### 4.3 自包含清单（**逐条核，缺一条就不算完成**）

AI 读完仓库应该能回答出下面每一个问题，做不到就说明缺文件：

- [ ] 帧长什么样？`{v,c,id,p,seq}` 各是什么？→ `protocol.md`
- [ ] 有哪些命令？网页→装置、装置→网页各是哪些？→ `protocol.md`
- [ ] `ARGX.fire('reveal')` 会让装置做什么？→ `event-vocabulary.md`
- [ ] 六个事件词分别是哪些，能不能自己发明？→ `event-vocabulary.md`（**答：不能**）
- [ ] `i` / `dur` / `ramp` / `pri` / `hold` 的取值范围与缺省？→ `parameters.md`
- [ ] `ARGX` 有哪些方法、参数、返回值？→ `sdk.md`
- [ ] 没插装置会怎样？→ `sdk.md` + `placement.md`（**答：静默降级，剧情照常**）
- [ ] 为什么不能 `ARGX.on('ack', () => 推进剧情)`？→ `placement.md`（**答：没买装置的人会卡死**）
- [ ] 一条 `err` 帧怎么读？→ `errors.md`
- [ ] 心跳、掉线、看门狗分别是多少秒？→ `constants.md`
- [ ] 现在什么能跑、什么跑不了（比如声音那路）？→ `hardware-limits.md`
- [ ] 交付哪些文件？→ `SKILL.md` 的「交付物」一节

### 4.4 五步工作流（写进 `SKILL.md` 的骨架）

```
1. 读代码    读创作者的网页源码，定位剧情状态机：翻页/点击/分支/解谜的成功点
2. 选模式    判断该走模式一还是模式二，把推荐与理由告诉创作者，由创作者拍板
3. 执行      按所选模式产出接入改动
4. 检验      用 prompts/verify.md 逐项核对生成结果
5. 交付      按清单交文件，并如实说明哪些没接、哪些做不到
```

### 4.5 两种模式

| | 模式一：讨论式 | 模式二：自主式 |
|---|---|---|
| 怎么开始 | AI 先给出**接入方案草案**（埋点位置表 + 事件映射），与创作者逐条讨论确认 | AI 先**问清偏好**，再一次性生成 |
| 适合 | 作品结构复杂、创作者有明确想法、有独特的剧情节奏 | 结构简单、创作者只想快点跑通 |
| 产出前必须 | 等待创作者确认埋点表 | 把「偏好问询清单」答完 |

**模式二必须先问的偏好**（写进 `prompts/mode-b-autonomous.md`，缺一项不许开工）：

1. 埋点密度：想密集（接近 8 个）还是克制（3–4 个）？
2. 哪些情节最该让房间动起来？（列出你识别到的候选，让作者挑）
3. 「揭示真相」那一刻用 `reveal` 还是 `danger`？
4. 结尾用 `ending`（灯常亮）还是 `reset`（熄灭回待机）？
5. 继电器那一路（如果装置有）要不要用？用在哪？
6. 要不要保留原页面的视觉风格，还是允许加一个「连接装置」按钮？

**模式选择的规则**：AI 必须**先给推荐+理由**，再由创作者选。
不要默默自己选。也不要两个模式一起跑（会产出两份冲突的改动）。

### 4.6 三个提示词（`prompts/` 下三份，都是可直接复制给 AI 的整段文本）

**`mode-a-discuss.md`** 必须包含：
- 让 AI 先输出「剧情节点清单」与「建议埋点位置表」（节点 / 位置 / 事件 / 理由）
- 明确「等创作者确认后再动代码」
- 给出需要创作者回答的问题（哪些节点是心跳变化点）

**`mode-b-autonomous.md`** 必须包含：
- 4.5 节那六个偏好问题
- 「问完再动手，一次产出」
- 产出后自动接第 4 步检验

**`verify.md`（检验提示词）**——**这是本阶段的重头**。要求：

- 逐项核对下列清单，每项给出**三选一结论 + 证据**：`符合` / `不符合` / `不适用`，
  证据必须指到**具体文件与行号或代码片段**。
- **禁止**出现「看起来没问题」「基本符合」这类无证据结论。
- 核对清单：
  1. 引入方式：`argx.js` 与原页面同目录或路径正确；未使用任何联网 CDN
  2. 连接由**真实用户点击**触发；页面加载时**不**自动连接
  3. 事件名**全部**来自六个词表，没有自造词
  4. 埋点数在 **3–8** 之间，且每个都能说清「这一刻玩家的心跳为什么变化」
  5. **没有**任何「等 `ack` 才推进剧情」的写法
  6. 没插装置时页面**不报错、不弹窗**，剧情能从头走到尾
  7. **没有**出现引脚电平（`GPIO4`、`HIGH`、`digitalWrite` 之类）
  8. 参数取值合法（`i` 0~1、`dur` 毫秒且不超 30s 缺省语义、`pri` 0~3）
  9. `ARGX.hint()` 非空时，页面上把它显示出来了
  10. 交付文件齐全（见 4.7）
- 结尾要求 AI 输出一张结论表 + 一句总结：**可以上线 / 需要修改（列出必须改的项）**。

### 4.7 交付物清单（**必须写进 `SKILL.md` 与 `verify.md`**）

接入完成后，AI 要交给创作者这四样：

| # | 交付物 | 内容要求 |
|---|---|---|
| 1 | **改动后的网页文件**（或 patch） | 只含接入所需的改动；每处改动旁有注释说明为什么埋在这里 |
| 2 | **`ARGS-INTEGRATION.md`**（接入说明） | 埋点表（节点 / 事件 / 参数 / 理由）、事件映射、改动了哪些文件与行、**哪些地方没接、为什么** |
| 3 | **检验结论** | 第 4.6 节 `verify.md` 的完整输出（十项结论表 + 总结） |
| 4 | **`argx.js`** | 从 skill 的 `assets/` 取一份放到作品目录，或按说明写清相对路径 |

> **第 2 项最容易漏。** 要求写「哪些没接、为什么」就是为了防止 AI 只报喜。

### 4.8 副本与防漂移（**第三份协议拷贝，必须小心**）

`argx-skill` 里会有 `protocol.md` 与 `argx.js` 的**副本**，加上主仓、`argx-esp32`，
协议一共**三份**。沿用 `argx-esp32` 已经确立的模式：

1. `references/protocol.md` 开头是副本标记：「⚠️ 本文档是副本，权威版本在主仓
   `https://github.com/ZhengTFB/argx/blob/main/protocol/PROTOCOL.md`」+ 同步方式。
2. `assets/argx.js` 头部加同格式注释：这是主仓 `sdk/argx.js` 的拷贝，
   SDK 行为改动必须两处一起改。
3. `argx-skill/README.md` 写明它与主仓、`argx-esp32` 的关系，并互链。
4. 主仓 `sdk/README.md` 与 `protocol/PROTOCOL.md` 各加一行回指 `argx-skill`。

### 4.9 硬性禁止（写进 `SKILL.md` 的「不要做」一节）

- **不要发明事件词。** 只有六个。创作者需要新词，说明这属于**改 SDK**，
  要停下来告诉创作者「这超出接入范围」——不要在作品里硬编码。
- **不要发引脚电平。** 只发语义（`light.main`），引脚由装置端决定。
- **不要让剧情判定依赖装置。** 没买装置的人必须能完整通关。
- **不要引入任何联网依赖。** 不许用 CDN、不许用外部字体、不许 `npm install`
  一个渲染库——SDK 是零依赖的单个 JS 文件。
- **不要动创作者没让你动的代码。** 只改接入所需的地方。

### 4.10 轻量自检 `tools/check-skill.mjs` + CI

理由：skill 是**给 AI 读的**，里面的代码块、路径、frontmatter 写错等于教错人，
而且这种错**人眼看不出来**。零依赖，三十来行：

- `SKILL.md` 有合法 YAML frontmatter（`name` / `description` 必填）
- 4.2 结构里列的文件**都存在**
- 所有 markdown 文件里引用的相对路径**都能解析到**
- `assets/argx.js`、`assets/argx.d.ts` 与主仓同名文件**逐字节一致**
  （不一致就红，这是防漂移最实在的一条）

CI（`.github/workflows/ci.yml`）：`node tools/check-skill.mjs`。

> 只在主仓时这可以省，但 skill 一旦发出去就有第三方依赖它，
> 这份自检是**最便宜的止损**。若你判断为负担，可以砍——但要在 `PROGRESS.md` 记一笔原因。

### 4.11 语言

- 正文**中文**（使用者是中文创作者与中文 AI）。
- `SKILL.md` 的 frontmatter `description` 里**中英关键词都要有**
  （`ARGX`、`ARG`、`alternate reality game`、`Web Serial`、`接入`、`埋点`），
  这样英文助手也能检索到。
- 代码与命令里的注释用中文（与主仓一致）。

  `prefers-reduced-motion` 的双重判断、总时长到点后的保底解除滚动锁（保底仍留 `TOTAL + 2000ms`）。

#### 5.3.3 `design/` 同步清单（**漏一处，下一轮 AI 就会改回去**）

`design/` 是界面真源。件六改了开场拍数与 hero 文案，**下面这几处记述必须同步改**，
否则下一个读 `design/` 的 AI 会照「三词」把改动推翻。逐处核，改完在汇报里列 `git diff`：

| 文件 | 改什么 |
|---|---|
| `design/prototype/index.html` | 开场层三个词 → 四个；时序按 5.3.2 重算。**首页 hero 文案、三卡、仓库区同步改** |
| `design/02-页面线框.md` §1.2–1.3 | 开场三词 → 四拍；hero 大标题的新文案 |
| `design/06-动效清单.md` §2.1 | 时序表：词数 3 → 4、总时长按重算值更新 |

> 这是「允许改的事实类改动」：界面真源里**描述首页文案与开场拍数**的记述跟着改，
> **控制台的一切不动**。
