## 1. 本阶段目标

让第三方作品能接进这套系统，并给出一个可以直接体验的示例。

三件产出物各司其职：

- **SDK** — 第三方 ARG 作者接入用的工具
- **Demo** — 示例作品，同时作为控制台「ARG 库」的第一条
- **AGENTS.md** — 让作者的 AI 知道怎么接

## 2. SDK 设计

### 2.1 硬约束

SDK 必须能**整段复制进第三方单文件 HTML 项目**，零依赖、纯原生 JS、无构建步骤。

理由：ARG 作者大量使用 AI 生成单文件 HTML 作品。让它 `npm install` 是失败率最高的操作——网络、版本、构建工具链任何一环出问题，AI 就会放弃并自己写一个不兼容的实现。

**不要用任何框架、打包工具、模块化方案。** 直接 `<script src="argx.js">` 可用。

### 2.2 核心原则

**静默降级**：`navigator.serial` 不存在、未连接硬件、连接失败——所有调用静默成功，绝不抛错、绝不弹窗、绝不阻塞剧情。

理由：作者在没硬件的机器上测试时，如果页面报错，他会认为 SDK 有 bug 然后删掉。

**模拟模式**：未连接硬件时把 cue 打到 console（如 `[ARGX] cue: lamp_on`）。这样作者不接硬件也能验证埋点是否正确，硬件依赖被完全从开发流程里剥离。

**极简门面**：作者侧只需要两三行。所有复杂度（握手、心跳、ACK、重连、看门狗）都在 SDK 内部。

### 2.3 file:// 协议检测

`file://` 下 `navigator.serial` 直接不存在——这是最高频的踩坑点，AI 生成的单文件 HTML 作者第一反应就是双击打开。

检测到时必须给出**可执行的人话提示**，例如：

> 检测到 file:// 协议，浏览器禁用了串口功能。请用本地服务器打开，例如在本目录执行 `npx serve` 或 `python -m http.server 8000`，然后访问 http://localhost:8000

只说"不支持"没有用，要给出下一步操作。

### 2.4 接口设计

对外暴露极简接口，参考形态（具体命名由你决定）：

```js
ARGX.init({ transport: 'mock' })   // 或 'serial'
ARGX.cue('light.main', { i: 0.8, ramp: 2000 })
ARGX.on('input', handler)          // 监听反向输入
```

**分层要求**：内部分为传输层 / 会话层 / 应用层。传输层实现 `connect` / `send` / `onMessage` / `close` 统一接口，与阶段一、二保持一致。将来加 WebSocket 等其他传输只加一个实现，上层不动。

即使对外只有三行，内部也要分层——这是总纲定的架构原则。

### 2.5 不支持直接下发引脚电平

SDK 只发语义 cue（如 `light.main`），不发 `GPIO4 HIGH`。硬件拓扑由设备端决定。

这条原则贯穿整个项目，在 SDK 文档中也要写明。

## 3. Demo 设计

### 3.1 要求

极简单画面，一两下操作就能触发，但要尽可能展示多种能力。

它是**双重身份**：既是交付物里的用法示例，也是控制台「ARG 库」的第一条作品。

### 3.2 建议形态

一个"老式终端"风格的单页：玩家面对几段加密文本，逐步解出线索。

触发点 3 个左右即可，不要多：

1. 打开页面 → `light.main` 缓慢渐暗（ambient，营造气氛）
2. 解开密码 → `light.main` 急闪 + `sound.beeper` 短响（high）
3. 最终解谜 → `light.main` 常亮 + 蜂鸣器长鸣（high）

具体剧情和视觉由你设计，以上是参考方向。

### 3.3 接入要求

Demo 必须**通过 SDK 接入**，不走后门直连。它要真实演示第三方作者怎么接这套系统——自己动手接一遍，才能验证 SDK 是否真的好用。

Demo 同时注册进控制台的 `works.ts`（阶段二已做的数据驱动列表），带硬件需求备注。

## 4. AGENTS.md（面向 AI 编码助手）

### 4.1 定位

这是本阶段**最有长期价值**的产出。

核心判断：**创作者的真实客户接口是他的 AI，不是创作者本人。** 作者不会来读文档，他的工作流是对 AI 说"给这场景加点氛围"。我们要让 AI 在这场对话里知道怎么接。

目标：任何一个 AI 编码助手在帮作者开发 ARG 时，读到这份文件就知道如何集成，且生成的埋点合理、克制、不会破坏剧情。

### 4.2 格式

用 **AGENTS.md 通用格式**（Linux Foundation 托管的开放标准，Claude Code、Cursor、Codex 等工具都支持）。

放在 SDK 目录根部，随 SDK 一起分发。

### 4.3 必备内容

**集成方式**：SDK 怎么引入、最少几行代码、怎么验证埋点生效。

**事件命名规范**：`场景.动作` 格式，如 `act2.ritual_start`、`act2.door_open`。给出推荐事件词表（氛围类如 tension / reveal / danger / calm），避免每个作者各起名字导致硬件端 cuelist 变成垃圾场。

**什么时候该埋点**：不是每个交互都埋，而是"玩家情绪转折点"——解谜成功、发现线索、进入新场景、Boss 出现。给判断标准，不只是 API 文档。

**克制原则**：一个 20 分钟的 ARG 场景，3–8 个 cue 就够。灯一直在闪等于没闪。这种审美约束必须写进去，否则 AI 会给每个按钮都加灯效。

**硬件不是判定源**：绝不把解谜正确性依赖在硬件上。没有装置也要能完整通关——这条是硬性要求。

**自检清单**：AI 完成后自己逐项验证——页面在 HTTPS 或 localhost 下、首次连接由真实点击触发、无硬件时不报错、console 能看到模拟 cue。

### 4.4 写法要求

**用肯定句写规则**。AI 对否定句服从度明显更低。

- 不写"不要在每个按钮上都加灯效"
- 写"一个场景保留 3–8 个 cue，只在情绪转折点触发"

**给示例代码胜过给描述**。完整可复制的代码片段，比三段文字有效。

**保持精简**。指令文件太长会让规则被稀释，重要内容放前面。
