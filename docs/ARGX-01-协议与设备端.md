## 3. 协议 v2 规范

### 3.1 设计目标

协议要像**脚手架**：内置一套基础能力，同时**允许使用者自定义函数**。加新功能时，协议本身不需要改。

这是整个项目最核心的设计，请优先保证它的可扩展性。

### 3.2 通用帧结构

```json
{"v":1,"c":"cue","id":"light.main","p":{"i":0.8,"dur":3000},"seq":42}
```

| 字段 | 含义 |
|---|---|
| `v` | 协议版本，将来不兼容升级靠它 |
| `c` | 命令类型 |
| `id` | 对象标识（命名空间） |
| `p` | 参数对象，所有具体行为都在参数里 |
| `seq` | 序号，用于 ACK 精确匹配 |

**传输规则**：每行一条 JSON，`\n` 结尾。接收方只处理以 `{` 开头的行，其余丢弃——ESP32 上电会输出 ROM 启动日志，会混在同一通道。

### 3.3 命令集（双向对称）

**网页 → 设备**

| 命令 | 用途 |
|---|---|
| `hello` | 要求设备自报家门 |
| `cue` | 触发一个输出效果 |
| `query` | 查询设备当前状态 |
| `cfg` | 下发配置（心跳周期等） |
| `ping` | 心跳 |
| `reset` | 强制回 idle，安全兜底 |

**设备 → 网页**

| 命令 | 用途 |
|---|---|
| `ready` | 连接即上报，含能力声明 |
| `ack` | 确认，带对应 `seq` |
| `state` | 响应 `query` |
| `input` | 物理输入事件 |
| `pong` | 心跳回应 |
| `err` | 错误上报 |

### 3.4 能力声明（可扩展性的核心）

设备连上时主动说清自己有什么：

```json
{
  "c":"ready","dev":"ARGX-0001",
  "caps":{
    "out":["light.main","sound.beeper"],
    "in":[],
    "proto":1
  }
}
```

上层据此自动适配。**加新硬件不需要改协议、不需要改上层逻辑**——只需在设备端注册一个新能力。

### 3.5 内置能力与命名空间

id 用 `域.对象` 格式。本期内置四种：

| id | 含义 |
|---|---|
| `light.main` | 灯光 |
| `sound.beeper` | 声音 |
| `motion.vibrate` | 振动 / 敲击 |
| `env.relay` | 环境（风扇、电磁锁等继电器类） |

将来加新能力（如 `display.oled`、`motion.servo`）时，在这张表追加即可，协议不改。

### 3.6 参数标准化

| 参数 | 含义 |
|---|---|
| `i` | intensity 强度 0~1，支持 PWM 调光、音量 |
| `dur` | duration 持续毫秒 |
| `ramp` | 渐变时长毫秒 |

```json
{"c":"cue","id":"light.main","p":{"i":0.2,"ramp":2000,"dur":5000}}
```

含义：2 秒内渐变到 20% 强度，保持 5 秒。

同一条协议，简单装置只取开关、高级装置做渐变——能力声明决定实现到什么程度。

### 3.7 反向通道（本期只留接口）

```json
{"c":"input","id":"switch.a","e":"press","v":1}
```

- `e` 事件类型：`press` / `release` / `hold` / `change`
- `v` 值

**本期实现要求**：固件提供 `InputRegistry` 输入注册接口，但不接任何实际硬件，`caps.in` 声明为空数组。将来接光敏电阻、物理开关、密码盘时，加一个注册即可，协议不改。

虚拟设备支持**手动注入 input 帧**，让反向链路现在就能验证。

### 3.8 会话层规则

- 收到未知 `c` 或未知 `id`：回 `err`，绝不崩溃
- 重复 cue（同 id 同 seq）：幂等，不重复执行
- 看门狗：15 秒未收到任何有效帧 → 自动回 idle，且该路径不可被抢占
- 上层每 3 秒发 `ping`，10 秒无 `pong` 判定掉线

看门狗的理由：玩家关掉浏览器后不能让灯一直亮着，这是真实事故而非理论风险。

## 4. 效果优先级

**抢占，不排队。** 理由：ARG 里最新事件必须立刻体现。排队会出现"谜题解开了灯还在演上一段"，沉浸感直接崩掉。

| 级别 | 值 | 用途 |
|---|---|---|
| `critical` | 0 | reset、看门狗。永远抢占，执行前清空队列 |
| `high` | 1 | 解谜成功、惊吓点等剧情关键节点 |
| `normal` | 2 | 默认。常规交互反馈 |
| `ambient` | 3 | 背景氛围。可被任何东西打断 |

**规则**：新效果优先级 ≥ 当前 → 抢占；否则直接丢弃。丢弃而非排队，避免 ESP32 内存被队列占满。

**保护机制**：
- 单效果 TTL 上限 30 秒，防止 bug 导致输出被永久占用
- 同 id 同优先级去重，防连点

**抢占后不自动恢复**——框架不管，交给应用层。自动恢复会让状态机复杂一倍，而多数场景并不需要。

### 5.1 固件要求

- 入口为单文件 `.ino`，内部按会话层 / 能力层组织
- **能力用注册式**，不用 switch-case：
  ```cpp
  node.onCue("light.main", [](Params p){ ... });
  ```
  加新能力 = 加一行注册，主循环不动
- 引脚号用 `#define` 定义在顶部
- 主输出建议 GPIO4。GPIO2 是 strapping pin，外接负载可能影响下载模式
- 调试日志用 `#` 前缀，与协议帧区分
- 依赖尽量少，JSON 可用极简手写解析

兼容性：代码同时在 ESP32-S3 和 ESP32-WROOM-32E 两种目标下可编译。

### 5.2 WIRING.md

写给不懂硬件的人看，要求具体、可执行：

- 每种能力（灯、蜂鸣器、振动马达、继电器）接哪个 GPIO
- 需要什么外围元件（如 LED 串 220–330Ω 电阻）
- 独立供电提醒：灯带、继电器不能从 ESP32 取电
- 常见接线错误

### 5.3 虚拟设备要求

这是本阶段的验证主力，要完整实现协议，不是"收到就回 ack"：

- 完整状态机：握手、能力声明、心跳、ACK、看门狗
- 实现全部四种能力，内部维护状态（不驱动真实硬件）
- 效果优先级抢占逻辑与固件一致
- 未知 id 回 `err`，忽略非法帧
- **对外暴露状态查询接口**——供阶段二的模拟器 UI 读取并绘制虚拟灯
- 支持手动注入 `input` 帧

### 5.4 故障注入

虚拟设备内置开关，用于验证上层健壮性：

- 不发 `ready`
- 延迟 3 秒应答
- 随机丢包
- 发送垃圾 JSON / 非 `{` 开头的行
- 中途断连

这些在真实硬件上很难复现，虚拟环境里是免费的。
