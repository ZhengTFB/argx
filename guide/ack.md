## 五种回执

| r | 意思 | 你该做什么 |
|---|---|---|
| applied | 执行了（含抢占） | 什么都不用做 |
| preempted | 执行了，并且抢掉了原来那个 | 同上 |
| dup | 去重了，没重复执行 | 同上 —— 这不是失败 |
| dropped | 按协议丢弃了（优先级不够） | 想让更强，把 pri 调小 |
| partial | batch 的回执，逐条结果在 res 里 | 看 res 里谁被丢了 |

> [!NOTE]
> dup 与 dropped 也要回 ack，否则上层分不清"装置收到了但按规则没做"与"帧根本没到"，前者会一直被误判成掉线。

## 连点去重

同一个能力、同样的优先级、**参数也一模一样**，且上一条还在跑时，第二次会被判定为重复点击，回 dup，不重新执行。

"参数也一模一样"这个条件是刻意加的。只按 id + 优先级去重时，氛围灯播放到一半无法再调亮度：调亮度本来就是同 id 同优先级，会被当成重复点击丢弃。

## 一帧发多个

```json
// [head]
{"v":1,"c":"batch","seq":31,"p":{"cues":[
  {"id":"light.main","p":{"i":1,"ramp":120,"dur":1500}},
  {"id":"sound.beeper","p":{"i":1,"dur":250}}
]}}
```

- 上限是 8 条、整帧不超过 512 字节
- **校验是原子的**：只要有一条 id 没注册，整批拒绝，一条都不执行
- 执行时各条各自仲裁（优先级是当前状态的函数，校验阶段判定不了）
- 回一个 ack，r 是共同结果或 partial，res 里逐条列出谁是什么结果
- **所有条目共用一个时间戳**，这是 batch 唯一的保证

> [!NOTE]
> 单独发两条 cue 之间隔着一次串口往返，十几毫秒的间隔使"灯和声音同时起"做不到。要同时，就必须在同一帧里。
