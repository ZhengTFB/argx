# ARGX 协议规范

| 项 | 值 |
|---|---|
| 文档修订 | v2 |
| 线上版本号 | `v: 1`（帧内字段） |
| 状态 | 权威来源。固件与网页端实现均从本文档派生 |
| 改协议的顺序 | 先改本文档 → 再改 `firmware/` 与 `device/virtual_device.js` |
| ESP32 侧参考实现 | [**`argx-esp32`**](https://github.com/ZhengTFB/argx-esp32) 仓库（本仓库的 `firmware/` 是它的拷贝） |

> 「文档修订 v2」与「线上版本号 `v:1`」是两件事：前者是本文档自身的修订次数，
> 后者是不兼容升级时才递增的线上字段。日常追加能力**不动** `v`。

---

## 1. 设计目标

协议要像脚手架：**内置一套基础能力，同时允许使用者自定义**。加新功能时协议本身不改。

具体到工程上只有一条硬要求：

> **`caps` 必须由能力注册表生成，任何地方不得手写第二份能力清单。**

只要这条成立，加一个 `display.oled` 就只是「写一个回调函数 + 注册一行」，
上层不需要升级、协议不需要改版本。

---

## 2. 传输与帧定界

| 项 | 规则 |
|---|---|
| 通道 | USB 串口（Web Serial）或 Mock |
| 编码 | UTF-8，每行一条 JSON |
| 定界 | `\n` 结尾；接收方需容忍 `\r\n` |
| 有效帧 | **只处理以 `{` 开头的行**，其余丢弃 |
| 单行上限 | 512 字节，超限丢弃该行（回 `err:bad_frame`） |
| 调试日志 | 以 `#` 开头，与协议帧同通道混流，接收方丢弃 |

只认 `{` 开头是硬规则：ESP32 上电会往同一通道吐 ROM 启动日志，
写死这条判定，两端都不用为「垃圾串扰」写特例。

---

## 3. 通用帧结构

```json
{"v":1,"c":"cue","id":"light.main","p":{"i":0.8,"dur":3000},"seq":42}
```

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `v` | int | 是 | 协议版本 |
| `c` | string | 是 | 命令类型 |
| `id` | string | 视命令 | 对象标识（命名空间） |
| `p` | object | 否 | 参数对象，**所有具体行为都在参数里** |
| `seq` | int | 否 | 序号，用于 ACK 精确匹配 |
| `dev` | string | 否 | 装置 ID，仅设备侧发出时携带 |

设计约定：**顶层字段只放路由信息，行为细节一律进 `p`。**
将来新增行为 = 新增 `p` 里的键，帧结构不变。

## 4. 命令集（双向对称）

两端跑同一套会话层，只是注册的处理器不同。命令集因此也是对称的。

### 4.1 网页 → 设备

| 命令 | `id` | 用途 | 设备应答 |
|---|---|---|---|
| `hello` | 否 | 要求设备自报家门 | `ready` |
| `cue` | 是 | 触发一个输出效果 | `ack` / `err` |
| `batch` | 否 | 一帧同时触发多个效果（见 §4.3） | `ack` / `err` |
| `query` | 否 | 查询当前状态 | `state` |
| `cfg` | 否 | 下发配置（心跳周期等） | `ack` |
| `ping` | 否 | 心跳 | `pong` |
| `reset` | 否 | 强制回 idle（安全兜底，critical 级） | `ack` |

### 4.2 设备 → 网页

| 命令 | 用途 | 触发时机 |
|---|---|---|
| `ready` | 连接即上报，含能力声明 | 传输层 connect 成功、收到 `hello` |
| `ack` | 确认，带对应 `seq` | 处理完任一网页帧 |
| `state` | 响应 `query` | 收到 `query` |
| `input` | 物理输入事件 | 设备侧事件发生 |
| `pong` | 心跳回应 | 收到 `ping` |
| `err` | 错误上报 | 见 §11 |

**对等性**：本文档描述的会话层、看门狗、优先级仲裁，两端实现完全一致。
设备端将来也可以发 `ping`、网页端也可以注册 `in` 能力——协议层面没有主从。

### 4.3 `batch`：一帧触发多个效果

```json
{"v":1,"c":"batch","seq":7,
 "p":{"cues":[
   {"id":"light.main","p":{"i":1,"ramp":500}},
   {"id":"sound.beeper","p":{"i":1,"dur":300}},
   {"id":"env.relay","p":{"i":1,"hold":true}}
 ]}}
```

每个 `cues[]` 元素的字段与一条独立 `cue` 完全一致（`id` + `p`），不引入新字段。
存在的理由：**同一帧里的效果在同一时刻生效**。

**原子性，分两个阶段，含义不同：**

| 阶段 | 规则 |
|---|---|
| **校验**（原子） | 全部元素的 `id` 都必须已注册、`p` 必须可解析、条数不得超过上限。**任一不合法 → 整批拒绝，一条都不执行**，回 `err`（`unknown_id` / `bad_frame`） |
| **执行**（各自仲裁） | 校验通过后逐条走 §10 的正常仲裁。某条被优先级丢弃或判为连点，是合法结果，不影响其它条 |

校验做不到「先问优先级」——优先级是本端当前状态的函数，只有执行时才知道。
但「整批要么一起被拒、要么一起提交」这半条是能保证的，而且是最有用的那半条：
不会出现「灯亮了、声音因为 id 拼错没响」的半截效果。

**应答**：整批回**一个** `ack`（网页端只等一个 `seq`），并带 `res` 逐条结果：

```json
{"v":1,"c":"ack","seq":7,"r":"partial",
 "res":{"light.main":"applied","sound.beeper":"dropped","env.relay":"applied"}}
```

`r` 是聚合结果：全部一致时取那个值；不一致时为 `partial`。
`res` 只在 `batch` 的 ack 上出现，普通 `cue` 的 ack 不带，避免日常帧变胖。

**约束**：

- 条数上限 8（`ARGX_MAX_BATCH`，见 §13）。超出 → `err:bad_frame`，无副作用
- 不允许嵌套：`cues[]` 里不能再放 `batch`
- 单帧总长仍受 512 字节限制，所以一批塞不下太多条——这是刻意的，
  一次要动十几个效果说明该在设备端定义一个组合能力，而不是让协议变大

## 5. 能力声明

设备连上时主动说清自己有什么：

```json
{
  "c":"ready","dev":"ARGX-0001","proto":1,
  "caps":{"out":["light.main","sound.beeper","motion.vibrate","env.relay"],"in":[]}
}
```

| 字段 | 含义 |
|---|---|
| `dev` | 装置 ID |
| `proto` | 协议版本，与帧内 `v` 同义（便于一眼确认） |
| `caps.out` | 可被 `cue` 的输出能力 id 列表 |
| `caps.in` | 可产生 `input` 的输入能力 id 列表 |

上层据此自动适配。**加新硬件不需要改协议、不需要改上层逻辑**——
只需在设备端注册一个新能力，`caps.out` 会自动多出一项。

设备收到 `query` 时回 `state`：

```json
{
  "c":"state","dev":"ARGX-0001","uptime":123456,
  "out":{"light.main":{"i":0.8,"pri":2,"ttl":2400},"sound.beeper":{"i":0.0,"pri":2,"ttl":0}},
  "in":{}
}
```

`ttl` 是剩余毫秒数（0 表示当前无生效效果）。没有生效效果的能力同样列出，`i:0`。

## 6. 命名空间与内置能力

id 采用 `域.对象` 格式。本期内置四种：

| id | 含义 | 参数用法 |
|---|---|---|
| `light.main` | 灯光 | `i` 亮度（PWM） |
| `sound.beeper` | 声音 | `i` 音量，`dur` 鸣响时长 |
| `motion.vibrate` | 振动 / 敲击 | `i` 强度，`dur` 时长 |
| `env.relay` | 环境（风扇、电磁锁等继电器类） | `i >= 0.5` 视为吸合 |

将来加新能力（`display.oled`、`motion.servo`…）在这张表追加一行即可，协议不改。
**设备端不认识的 `id` 一律回 `err:unknown_id`，不崩溃。**

## 7. 参数标准化

| 参数 | 类型 | 缺省 | 含义 |
|---|---|---|---|
| `i` | float | 1.0 | intensity 强度 0~1，支持 PWM 调光、音量 |
| `dur` | int ms | 30000 | duration 持续毫秒（上限见下） |
| `ramp` | int ms | 0 | 渐变时长毫秒 |
| `pri` | int 0~3 | 2 | 优先级，见 §10 |
| `hold` | bool | false | 常驻：忽略 `dur`，效果保持到被抢占或复位（见下） |

```json
{"c":"cue","id":"light.main","p":{"i":0.2,"ramp":2000,"dur":5000}}
```

含义：2 秒内渐变到 20% 强度，保持 5 秒。

- `i` 超出 0~1 → 钳制，不报错
- `dur` > 30000 → 钳制到 30000
- `dur` 缺省即 30000（也就是上限）——**任何效果最长活 30 秒**，防止 bug 导致输出被永久占用
- `ramp` > `dur` → 钳制到 `dur`

### 7.1 `hold`：常驻效果

```json
{"c":"cue","id":"light.main","p":{"i":1,"hold":true}}
```

「最终解谜成功，灯就一直亮着」这类需求，靠默认的 30 秒 TTL 做不到
（只能每 30 秒重发一次，丑且不可靠）。`hold:true` 明确表达「这个效果不设时限」。

| 规则 | 说明 |
|---|---|
| `dur` 被忽略 | 写了也不生效。`hold` 的含义就是没有时限，两个字段打架时以 `hold` 为准 |
| `ramp` 照常生效 | 常驻不等于没有渐变。`ramp` 的上限此时按 30000 单独钳制，不受 `dur` 影响 |
| `state.ttl` 报 `-1` | 正常效果的 TTL 恒 ≥ 0，所以 `-1` 可以无歧义地表示「常驻」 |
| 被抢占即结束 | 优先级规则（§10）完全不变，`hold` 不是无敌 |
| 看门狗/reset/断连一律清掉 | **这一点是硬要求**，见下 |

**`hold` 不绕过看门狗。** 15 秒收不到任何有效帧，一切输出归零，常驻效果也一样。
所以「玩家关掉浏览器，灯一直亮到天亮」这个事故仍然不会发生——
`hold` 放开的是 30 秒 TTL，不是安全兜底。写设备端实现时这条不许打折。

同一条协议，简单装置只取开关（`i >= 0.5` 即亮），高级装置做渐变——
实现到什么程度由设备端决定，符合「不下发引脚电平」的约束。

## 8. 反向通道

```json
{"c":"input","id":"switch.a","e":"press","v":1}
```

| 字段 | 含义 |
|---|---|
| `e` | 事件类型：`press` / `release` / `hold` / `change` |
| `v` | 值 |

本期 `caps.in` 声明为空数组，设备端只提供注册接口，不接任何实际硬件。
将来接光敏电阻、物理开关、密码盘时加一个注册即可，协议不改。
虚拟设备支持手动注入 `input` 帧，反向链路现在就可验证。

## 9. 会话层规则

### 9.1 时序

```
设备                                 网页端
  │  connect 成功                        │
  │ ─────── ready(dev, caps) ──────────▶ │  连接即上报
  │ ◀────────── hello ───────────────── │  （可选）
  │ ─────── ready(dev, caps) ──────────▶ │
  │ ◀────────── ping ────────────────── │  每 3 秒
  │ ─────── pong(seq) ─────────────────▶ │
  │ ◀────────── cue(id, p, seq) ─────── │
  │ ─────── ack(seq) ──────────────────▶ │
```

### 9.2 规则

- **未知 `c`** → 回 `err:unknown_cmd`，绝不崩溃
- **未知 `id`** → 回 `err:unknown_id`
- **重复 cue（同 id 同 seq）** → 幂等，不重复执行，回 `ack` 带 `r:"dup"`
- **心跳**：网页端每 3 秒发 `ping`，10 秒无 `pong` 判定掉线（判定权在发起方）
- **看门狗**：设备端 15 秒未收到任何有效帧 → 自动回 idle，**该路径不可被抢占**
- **降级优于报错**：参数越界一律钳制，`file://`、无硬件、连接失败一律静默成功

### 9.3 设备端会话状态机

| 状态 | 含义 | 迁移 |
|---|---|---|
| `disconnected` | 未连接 | `connect` → `ready` |
| `ready` | 已上报 `ready`，等首个有效帧 | 收到任一有效帧 → `active` |
| `active` | 会话中，看门狗计时 | `>10s` 无 `ping` → `stale`；`>15s` 无有效帧 → `idle` |
| `stale` | 对端可能掉线（**仅置标志，不灭自己的输出**） | 收到任一有效帧 → `active` |
| `idle` | 看门狗触发的安全态 | 复位完成后收到任一有效帧 → `active` |

`stale` 不切断输出是刻意的：掉线判定是发起方的事，
网络抖动十几秒就让玩家的灯灭掉，比灯多亮一会儿糟糕得多。

**`idle` 的复位路径不可被抢占**：复位过程中置 `resetting` 标志，
期间到达的普通 `cue` 一律丢弃（回 `ack` 带 `r:"dropped"`），
复位完成后才恢复接收。这条保证「玩家关掉浏览器后灯一定会灭」。

看门狗的理由：玩家关掉浏览器后不能让灯一直亮着，这是真实事故而非理论风险。

## 10. 效果优先级与仲裁

**抢占，不排队。** ARG 里最新事件必须立刻体现；排队会出现「谜题解开了，
灯还在演上一段」，沉浸感直接崩掉。

| 级别 | 值 | 用途 |
|---|---|---|
| `critical` | 0 | reset、看门狗。永远抢占，执行前清空所有输出 |
| `high` | 1 | 解谜成功、惊吓点等剧情关键节点 |
| `normal` | 2 | 默认。常规交互反馈 |
| `ambient` | 3 | 背景氛围。可被任何东西打断 |

### 仲裁顺序（每个能力独立维护当前效果）

1. **复位中** → 丢弃（`r:"dropped"`）
2. **同 id 同 seq** → 幂等，不执行（`r:"dup"`）
3. **同 id、同 `pri`、同参数、仍在生效期内** → 视为连点，丢弃（`r:"dup"`）
   （参数不同则照常执行，否则就没法在氛围播放中途调亮度了）
4. **新 `pri` <= 当前 `pri`，或当前无效果** → 抢占执行（`r:"applied"`）
5. **新 `pri` > 当前 `pri`** → 丢弃（`r:"dropped"`）

`critical` 额外做一件事：执行前对**所有**能力走一遍复位（清空输出），再应用自己。

**抢占后不自动恢复**——框架不管，交给应用层。
自动恢复会让状态机复杂一倍，而多数场景并不需要。

**TTL**：任一被接受的效果都会记 `expiresAt = now + min(dur, 30000)`；
到点自动对该能力执行释放（`i:0`），不需要任何人再发帧。
`hold:true` 的效果不记 `expiresAt`（§7.1），但仍然会被抢占、reset、看门狗清掉。

**同一帧内的时间戳**：`batch` 里所有条目共用同一个 `now`，
所以「灯和声音同时开始」是有保证的，不存在帧与帧之间的时序偏差。
单独发两条 `cue` 则**没有**这个保证——两帧之间隔着一次串口往返，
真需要同步就用 `batch`，这也是它存在的全部理由。

## 11. 错误码

| code | 触发 |
|---|---|
| `bad_frame` | 行以 `{` 开头但解析失败 / 缺必填字段 / 超 512 字节 |
| `unknown_cmd` | `c` 不在命令集内 |
| `unknown_id` | `cue` 的 `id` 未注册 |
| `unknown_input` | 注入的 `input` id 未在 `caps.in` 内 |
| `bad_version` | `v` 与本端不兼容 |

```json
{"v":1,"c":"err","code":"unknown_id","msg":"light.nope","seq":42,"id":"light.nope"}
```

`err` 是**上报**不是**崩溃**：报完继续正常工作，会话不断。

## 12. 扩展指南

### 加一个输出能力（例：`display.oled`）

| 文件 | 改动 |
|---|---|
| `firmware/capabilities.cpp` | 写一个回调（约 15 行）+ 一行 `node.onCue("display.oled", …)` |
| `device/virtual_device.js` | 同一形状的注册表加一条（约 5 行） |
| `protocol/PROTOCOL.md` | §6 的能力表追加一行 |
| `tests/frames.json` | 可选：加两条帧 |

会话层 `argx_node.*` **零改动**，`v` 不变，上层不需要升级。
`caps.out` 由注册表遍历生成，不需要手写。

### 加一个输入能力（例：`switch.a`）

`node.onInput("switch.a", fn)` 注册 → `caps.in` 自动多一项 →
事件发生时 `node.emitInput("switch.a","press",1)` 发出 `input` 帧。

### 什么时候才需要动协议本身

先分清两种改动的代价：

| 改动 | 老设备的表现 | 要升 `v` 吗 |
|---|---|---|
| **新增**一条命令（如 `batch`） | 回 `err:unknown_cmd`，会话不断 | 不用 |
| **新增**一个可选参数（如 `hold`） | 忽略，按缺省行为执行 | 不用 |
| **新增**一个能力 id | 回 `err:unknown_id` | 不用 |
| **改变**已有字段的含义、类型或结构 | 静默按错误的方式执行 | **必须** |

原则：**新增是安全的，改变才是破坏性的**。老设备对新东西的反应必须是
「明确拒绝」或「按缺省降级」，绝不能是「理解错了还照做」。
只要满足这条，`v` 就不动。

需要升 `v` 的典型情况：帧定界方式变化、需要二进制通道、
需要请求-响应式的多轮交互、需要把 `p` 从对象改成分层结构。

## 13. 常量总表

**本节是唯一真值来源。固件与虚拟设备必须共用同一份，不得各写一套。**

| 常量 | 值 |
|---|---|
| 帧定界 | 每行一条 JSON，`\n` 结尾 |
| 有效帧判定 | 只处理以 `{` 开头的行 |
| 单行上限 | 512 字节 |
| 心跳间隔 | 3 秒（网页端发 `ping`） |
| 掉线判定 | 10 秒无 `pong` |
| 看门狗 | 15 秒无有效帧 → 自动回 idle，路径不可抢占 |
| 单效果 TTL | 上限 30 秒（`hold:true` 例外，见 §7.1） |
| 批量上限 | 8 条 / 帧（`batch`，见 §4.3） |
| 协议版本 | `v: 1` |
| 主输出引脚 | GPIO4 |
| 调试日志前缀 | `#` |

## 附：与任务书 3.x 的差异记录

以下为落地时做的协议小改动（新增可选字段 / 明确未定义行为），已在本文档就地生效：

1. **`ack` 增加可选 `r` 字段**（`applied` / `preempted` / `dup` / `dropped`）。
   理由：所有被正常处理的 `cue` 都回 `ack`，避免「因优先级丢弃而误判掉线」；
   `r` 让网页端能区分「执行了」和「按协议丢弃了」。
2. **明确 `dur` 缺省 = 30000**。任务书只说 TTL 上限 30 秒，没说缺省；
   不明确的话「缺省 dur」的效果会永久占用输出，正好是 TTL 要防的那个 bug。
3. **`ready` 增加可选 `proto` 字段**，与帧内 `v` 同义，便于人工排查时一眼确认。
4. **连点判定纳入参数比较**（§10 第 3 条）。纯「同 id 同优先级去重」会导致
   氛围播放中途无法调亮度，是明显的可用性缺陷。
5. **新增 `batch` 命令**（§4.3）。理由：单发多条 cue 之间隔着串口往返，
   做不到「灯和声音同时起」。阶段三的 Demo 必然需要。
   保持 `v:1`：老设备收到 `batch` 会回 `err:unknown_cmd`，会话不断，符合降级原则。
6. **新增 `hold` 可选参数**（§7.1）。理由：`dur` 缺省 30000 意味着
   「最终解谜后灯常亮」做不到。保持 `v:1`：老设备忽略未知参数，
   退化成 30 秒效果，语义可接受，不会出错。
